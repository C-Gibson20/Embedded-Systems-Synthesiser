# 7. CAN Communication
[Back to Table of Contents](README.md)

The synthesiser supports distributed operation through communication over a Controller Area Network (CAN) bus. This allows multiple devices to exchange musical events and operate as a coordinated network of synthesisers.

Incoming and outgoing messages represent musical control events such as key presses and parameter changes. These events are encoded into compact CAN messages that can be transmitted efficiently across the network.

## 7.1 Message Format

Each CAN message contains a fixed-length payload describing a musical event. The structure of the message payload is shown in Table 1.

| Byte | Meaning |
| --- | --- |
| 0 | Message type |
| 1 | Key index |
| 2 | Pitch |
| 3 | Waveform |
| 4 | Octave |
| 5 | Volume |

This compact encoding allows musical events to be transmitted with minimal bandwidth while preserving the parameters required for synthesis.

## 7.2 Communication Architecture

CAN communication is integrated with the task-based architecture using interrupt-driven reception and queue-based message handling.

Incoming CAN frames are captured by the CAN receive interrupt handler and placed into a FreeRTOS message queue. The `decodeTask` thread then processes queued messages and converts them into synthesiser control commands.

Outgoing messages are generated by application tasks and placed into a transmit queue. The `CAN_TX_Task` thread retrieves messages from this queue and initiates CAN transmission.

This design decouples the time-critical interrupt handling from the higher-level message processing. CAN message processing is implemented as a lower-priority task, ensuring that communication activity cannot interfere with the timing constraints of the audio synthesis subsystem.
