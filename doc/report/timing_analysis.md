# 4. Task Timing Characterisation
[Back to Table of Contents](README.md)

This file characterises the timing behaviour of each task in the system. For schedulability analysis under the RMS model, each task must be associated with a minimum initiation interval (period) and WCET.

## 4.1 Task Classification

Tasks in the system can be classified according to the strictness of their timing requirements.

| Task | Type | Reason |
| --- | --- | --- |
| `sampleGenTask` | Hard real-time | Audio samples must be generated before the DAC requires new data |
| `scanKeysTask` | Firm real-time | Delayed key detection degrades responsiveness but does not break system operation |
| `decodeTask` | Firm real-time | Delayed processing of CAN messages may introduce latency but does not break system operation |
| `knobTask` | Firm real-time | Delayed processing of encoder input degrades responsiveness but does not break system operation |
| `CAN_TX_Task` | Firm real-time | Transmission delays may introduce latency but does not break system operation |
| `displayUpdateTask` | Soft real-time | Display updates are not time-critical. |
| `dinoTask` | Soft real-time | Delayed game updates affects only responsiveness of the optional game mode. |

Hard real-time tasks must always meet their deadlines, while firm and soft real-time tasks tolerate occasional delays without system failure.

## 4.2 Task Periods and Minimum Initiation Intervals

The timing behaviour of each task is characterised by its period for periodic tasks or minimum inter-arrival time for event-driven tasks. These values are used in the schedulability analysis.

Some tasks in the system are triggered by external events rather than fixed periods. 

For example:

- CAN receive events are limited by the CAN bus throughput.
- Key press events are limited by human interaction speed.
- Encoder interrupts occur only when the user rotates a control.

For schedulability analysis, the worst-case arrival rate of these events is used to derive an equivalent minimum initiation interval.

| Task | Type | Period / Minimum Inter-Arrival $T_i$ | Trigger |
| --- | --- | --- | --- |
| `sampleGenTask` | Periodic<br>(DMA-triggered) | $T_{DMA} = 5.82\ \text{ms}$ | DMA buffer completion |
| `scanKeysTask` | Periodic | $T_{scan} = 20\ \text{ms}$ | `vTaskDelayUntil()` |
| `decodeTask` | Sporadic | $T_{CAN} = 120\ \mu s$<br>Worst-case | CAN RX interrupt |
| `knobTask`<br>I2C expander mode only | Sporadic | $T_{knob} =5\ \text{ms}$  | Encoder interrupt |
| `CAN_TX_Task` | Sporadic | $T_{CAN\_TX} = 1.67\ \text{ms}$<br>Bounded by scan rate | Queue enqueue |
| `displayUpdateTask` | Periodic | $T_{display} = 100\ \text{ms}$ | `vTaskDelayUntil()` |
| `dinoTask` | Periodic | $T_{dino} = 60\ \text{ms}$ | `vTaskDelayUntil()` |

Periodic tasks are implemented using the FreeRTOS `vTaskDelayUntil()` function, ensuring deterministic activation intervals. Event-driven tasks are modelled as sporadic tasks with bounded minimum inter-arrival times derived from hardware or system constraints.

## 4.3 Worst Case Execution Time

The WCET $C_i$ represents the maximum time required for a task to complete its execution under all possible conditions.

Execution times are measured using runtime instrumentation based on the `micros()` timing function. 

| Task | WCET V1 $C_i, \mu s$ | WCET V1 with Dino $C_i, \mu s$ | WCET V2 (I2C Expander)  $C_i, \mu s$ | WCET V2 (I2C Expander) with Dino $C_i, \mu s$ |
| --- | --- | --- | --- | --- |
| `sampleGenTask` | 821.78 | 822.00 | 821.44 | 821.94 |
| `scanKeysTask` | 234.44 | 234.41 | 225.91 | 226.41 |
| `decodeTask` | 13.59 | 14.16 | 14.34 | 14.84 |
| `knobTask` | N/A | N/A | 226.81 | 227.91 |
| `CAN_TX_Task` | 6.06 | 6.03 | 5.56 | 6.13 |
| `displayUpdateTask` | 19160.91 | N/A | 12206.44 | N/A |
| `dinoTask` | N/A | 14160.87 | N/A | 7211.72 |
| `CAN_RX_ISR` | 4.06 | 3.88 | 3.84 | 3.88 |
| `CAN_TX_ISR` | 2.81 | 2.66 | 2.69 | 2.72 |
| `knobISR` | N/A | N/A | 2.72 | 2.72 |

To obtain conservative WCET estimates, worst-case workloads were artificially constructed during profiling. 

For example, the audio synthesis task was evaluated with all voices active simultaneously and configured to use the most computationally expensive waveform implementation. This configuration maximises the amount of waveform generation and mixing performed during each synthesis cycle, ensuring that the measured execution time represents the upper bound of expected runtime behaviour. 

The resulting execution times are therefore conservative estimates suitable for use in subsequent schedulability analysis.

## 4.4 Queue-Based Rate Decoupling

FreeRTOS queues are used extensively to decouple producer and consumer tasks. This mechanism allows bursts of events generated by interrupts to be buffered and processed asynchronously by worker threads. As a result, the effective workload experienced by a task becomes bounded by the queue processing rate rather than the instantaneous burst rate of external events. This smoothing effect simplifies schedulability analysis by reducing short-term scheduling pressure.

## 4.5 Deterministic and Non-Deterministic Execution

Most tasks in the system execute deterministic code paths whose execution time depends only on bounded loops and arithmetic operations.

However, certain operations introduce limited non-determinism, including:

- Peripheral communication latency.
- Library function execution time.
- Variability in interrupt arrival timing.

These factors are accounted for during WCET measurement to ensure that the timing model used for scheduling analysis remains conservative.
